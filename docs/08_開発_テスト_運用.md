# 08 開発・テスト・運用設計

## 1. 開発フェーズ

### Phase 0：技術検証

- C#でローカルTCPプロキシを作る。
- 別PCのMinecraft ServerへTCP転送する。
- 2台のWindows PCでログインできることを確認する。
- 切断、再接続、大きなチャンク読み込みを確認する。

### Phase 1：Relay MVP

- RelayをVPSへ配置する。
- ホスト・ゲストの紐付けを固定IDで実装する。
- TCP双方向転送を実装する。
- 転送量、遅延、メモリ使用量を測定する。

### Phase 2：GUI MVP

- WinUI 3でホーム、公開、参加、ログ、設定画面を作る。
- 参加コードを実装する。
- エラーを利用者向け文言へ変換する。
- システムトレイ動作を実装する。

### Phase 3：安全性・配布

- TLS、トークン、レート制限を実装する。
- インストーラーまたはMSIXを作成する。
- コード署名、自動更新を検討する。
- クローズドテストを行う。

### Phase 4：拡張

- Minecraft統合版のUDP転送
- 複数Relay地域
- アカウントとフレンド
- ホスト承認、ブロックリスト

## 2. テスト方針

| 種別 | 対象 |
|---|---|
| 単体試験 | コード検証、状態遷移、フレーム処理、設定 |
| 結合試験 | Client–Relay–Client間の接続と再接続 |
| E2E試験 | Minecraftから実際にログイン・プレイ |
| 性能試験 | 同時接続数、帯域、CPU、メモリ、遅延 |
| 障害試験 | Relay停止、回線断、ホスト停止、ポート競合 |
| セキュリティ試験 | 総当たり、無効トークン、巨大フレーム、レート制限 |
| UI試験 | 画面倍率100〜200%、ダーク・ライト、キーボード操作 |

## 3. MVP合格基準

- ポート開放なしで別回線のゲスト1名がJava版サーバーへ参加できる。
- 30分以上プレイして通信が継続する。
- ホスト・ゲストの異常終了後に再起動できる。
- 参加コードなしでデータチャネルを確立できない。
- Relayへ送信したMinecraftデータがログやDBに保存されない。
- 初回利用者が説明書なしで公開・参加を完了できる。

## 4. CI/CD

```text
Pull Request
  → dotnet format確認
  → ビルド
  → 単体試験
  → 結合試験
  → 成果物生成
  → 署名
  → テスト配布
```

Relayはコンテナ化し、ステージングで疎通後に本番へ反映する。DBマイグレーションはアプリ起動時の無条件実行ではなく、リリース工程で明示的に実行する。

## 5. 監視項目

- Relay稼働率
- 現在の接続数、ルーム数
- 新規接続成功率
- API応答時間
- Relay地域ごとの遅延
- 送受信帯域
- CPU、メモリ、接続ソケット数
- 認証失敗とレート制限発生数
- アプリバージョン別の障害数

## 6. 配布方針

- 初期はWindows x64のみ提供する。
- 署名済みMSIXまたは署名済みインストーラーを第一候補とする。
- 自己完結型として必要な.NETランタイムを同梱する。
- 安定版とテスト版の更新チャネルを分ける。
- 旧バージョンを即時停止せず、最低対応バージョンをAPIから通知する。

## 7. 最初の実装タスク

1. Visual StudioでWinUI 3ソリューションを作成する。
2. `MineLink.Core`にTCPコピー処理を実装する。
3. コンソール版Host・Guestでローカルネットワーク試験を行う。
4. Relayを追加して外部回線試験を行う。
5. 通信コアが安定してからWinUI 3へ組み込む。

GUIから着手してもよいが、最初に通信部分を小さなコンソール試作で検証する。通信方式の成立前に画面を作り込みすぎないことを推奨する。
