# 07 セキュリティ設計

## 1. 想定する脅威

- 参加コードの総当たり
- トークンの盗難・再利用
- Relayへの大量接続
- 不正なフレーム長によるメモリ消費
- 中間者攻撃
- なりすましクライアント
- ホストPC上の意図しないサービスへの接続
- ログからの秘密情報漏えい

## 2. 認証・認可

- 参加コードは暗号学的乱数から生成する。
- DBには参加コードをそのまま保存せず、検索可能な安全な形式を検討する。
- 参加コードには有効期限を設定する。
- ホスト用・ゲスト用トークンを分離する。
- トークンはルーム、役割、期限、クライアントへ紐づける。
- ホスト操作はホスト権限を持つトークンだけに許可する。
- ルーム参加とコード検証にIP・端末単位のレート制限を行う。

## 3. 通信保護

- TLS 1.3を優先する。
- 証明書検証を無効化するオプションは提供しない。
- API、WebSocket、データチャネルをすべて暗号化する。
- TLS終端後のRelay内部でも、不要なパケット記録を行わない。
- 将来的にクライアント間E2E暗号化を追加可能な構造にする。

## 4. ローカル保護

- ゲスト待受は初期値で`127.0.0.1`だけにバインドする。
- `0.0.0.0`での待受は初版では許可しない。
- ホスト転送先は初期値でループバックアドレスに限定する。
- 任意アドレスへの転送は詳細設定として警告を表示する。
- 秘密情報はCredential LockerまたはDPAPIで保護する。
- アップデートファイルの署名とハッシュを検証する。

## 5. Relay防御

| 対策 | 内容 |
|---|---|
| 接続上限 | ルーム、IP、トークン単位で制限 |
| 帯域制限 | 異常な転送量を検出・抑制 |
| サイズ検証 | フレーム長に上限を設定 |
| タイムアウト | 無通信・未認証接続を終了 |
| バックプレッシャー | 送信遅延時にメモリを無制限に使用しない |
| 監査 | ルーム操作と拒否理由を記録 |

## 6. プライバシー

- 収集データと保持期間を明示する。
- Minecraft通信内容を解析・保存しない。
- クラッシュレポート送信は利用者の同意を得る。
- 診断ログを共有する前に秘密情報を自動マスキングする。

## 7. 注意事項

中継方式はポート開放を不要にできるが、「どの環境でも必ず接続できる」「攻撃を完全に防げる」とは保証しない。企業・学校ネットワークでは、外向きWebSocketや長時間TCP接続が制限される場合がある。
